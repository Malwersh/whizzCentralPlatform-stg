# خطة انتقال تطبيق المطعم: المالك والمطاعم والفروع والموظفون

تاريخ الفحص: 2026-10-14. النطاق: مستودعات Staging. هذه خطة تنفيذ مقترحة، وليست إعلانًا بأن الميزات نُفذت. لم تتغير التطبيقات أو الخدمات المنشورة بسبب هذه المراجعة.

## 1. القرار المقترح

حساب شخصي موثّق بالهاتف، ثم مساحة «مطاعمي» لإدارة الأنشطة والفروع. لكل فرع مراجعة وتفعيل مستقلان، ومحفظة وطلبات وموقع وساعات عمل مستقلة. الموظفون أشخاص مستقلون، يحصلون على عضويات وصلاحيات محددة. جهاز الفرع المعتمد يستقبل الطلبات، ويمكن للموظف فتح مهامه بالـPIN دون أن يؤدي قفل جلسته إلى إيقاف استقبال الطلبات. يمكن للمالك والموظف المالي استعمال هاتفهما الشخصي بالصلاحيات نفسها التي يطبقها الخادم.

لا نطلب من المالك إنشاء حساب هاتف جديد لكل فرع، ولا نشارك حسابه الشخصي مع الموظفين. تسجيل الهاتف يثبت امتلاك الرقم، وليس ملكية المطعم أو صحة مستنداته.

## 3. حالة التطبيق الحالية المثبتة من الكود

- `whizzMerchants-stg/frontend/lib/screens/registration_form_screen.dart`: الاسم الشخصي والهاتف والبريد الاختياري وبيانات المطعم والعنوان والصورة والمستندات في تسجيل واحد؛ رفع الملفات يسبق استدعاء `registerWithBusiness`.
- `backend/functions/auth/unified_auth_handler.js`: التسجيل ينشئ هوية Cognito والمطعم معًا، ويربط `ownerId` و`cognitoUserId` بالشخص. المطعم يُنشأ `status=pending` ومعه `isActive=true`. هذا يحتاج توحيد قواعد الأهلية؛ لا يكفي وحده لإثبات أن المطعم يظهر للعملاء قبل الاعتماد.
- `frontend/lib/services/app_auth_service.dart`: `confirmPhoneCode` يختار `businesses.first` ويربط حالة الدخول بحالة المطعم الأول. هذا لا يلائم تعدد الفروع أو وجود فرع قيد المراجعة وآخر فعال.
- `frontend/lib/main.dart`: توجد شاشة حسابات محافظ لمن ليس لديه مطعم مختار، لكنها تحتاج التحول إلى مساحة إدارة أعمال واضحة.
- `backend/functions/auth/merchant_business_list.js`: يعرض الأعمال المملوكة وفق هوية موثقة، ويستبعد سجلات الحذف؛ يعتمد Scan متكررًا، فيحتاج فهارس مناسبة قبل التوسع.
- `frontend/lib/screens/merchant_finance_members_screen.dart`: منح/سحب صلاحية مالية موجود، ويستخدم مسار `members`. ليس نظامًا متكاملًا لمديري الفروع والاستقبال والدعوات والتبديل بالـPIN.
- مسارات حذف الشخص وإغلاق المطعم وإزالة العضوية بُنيت واختُبرت سابقًا؛ يجب مراجعة تكاملها مع كل كيان وصلاحية وجهاز جديد. وثيقة الحذف تضم مراحل تاريخية؛ لا تُقرأ مقدمتها القديمة كحالة التنفيذ الحالية.

هذا فحص موجّه لمسارات التسجيل والدخول والعضويات، وليس ادعاء بمراجعة كل مسار في الخدمات. المرحلة الأولى أدناه تُكمل جرد جميع مستهلكي بيانات المطاعم قبل التعديل.

## 4. نموذج البيانات والهوية

| الكيان | مسؤوليته |
|---|---|
| الشخص | هوية Cognito ثابتة، اسم، هاتف موثق، بريد تواصل اختياري؛ حالة تحقق ومراجعة منفصلة عن حالات المطاعم |
| النشاط | جهة الملكية والإدارة، المالك، الاسم القانوني عند الحاجة؛ يحتضن علامة واحدة أو أكثر |
| العلامة/المطعم | الاسم التجاري مثل البركة أو سنونو، الشعار، قائمة مرجعية اختيارية |
| الفرع | موقع فعلي، منطقة خدمة، ساعات، وسيلة اتصال تشغيلية، حالة اعتماد، طلبات ومحفظة وإعدادات مستقلة |
| العضوية | شخص + نطاق نشاط/فروع + دور وصلاحيات وإصدار وحالة؛ مصدر التفويض وليس رقم الهاتف وحده |
| الدعوة | رقم موثق مستهدف، صلاحيات ونطاق، انتهاء، قبول/إلغاء؛ لا تنشئ ملكية تلقائيًا |
| جهاز الفرع | جهاز معتمد لفرع محدد، إذن استقبال محدود، آخر اتصال وإصدار واعتماد/إلغاء |
| جلسة الموظف | الشخص الفاعل على جهاز معتمد، نطاق وصلاحيات ومدة قصيرة؛ مستقلة عن استقبال الطلبات |

معرفات المطاعم الحالية `businessId` تبقى معرفات الفروع التشغيلية أثناء الانتقال؛ نضيف روابط النشاط والعلامة دون إعادة ترقيم الطلبات أو المحافظ. لا تُدمج محافظ الفروع تلقائيًا. فهارس العضويات بالهوية والفروع بالمالك/النشاط تمنع الاعتماد الدائم على Scan.

## 5. رحلة المالك والمراجعة

1. الاسم ورقم الهاتف وقبول الشروط، ثم OTP. البريد اختياري؛ لا نعيد كلمة المرور لمسار الهاتف.
2. يدخل «مطاعمي» ويستطيع حفظ مسودة نشاط وفرع ومتابعة المراجعة. حساب الشخص لا يتوقف لأن أحد فروعه قيد المراجعة.
3. إضافة مطعم جديد أو فرع لعلامة موجودة: الاسم، المحافظة والقضاء والمنطقة، دبوس GPS، وصف العنوان، رقم تواصل الفرع، التصنيف، الساعات والصورة.
4. معلومات إثبات الملكية/التفويض والمستندات المطلوبة تعرض حسب نوع النشاط والسياسة المحلية التي تعتمدها الإدارة. لا نفرض قائمة أجنبية دون مراجعة عراقية.
5. إعداد القائمة والدفعات وقبول اتفاقية الشراكة؛ رفع الملفات بعد تسجيل الدخول إلى S3 Staging مع روابط مؤقتة وحماية المستندات، وتنظيف المرفقات اليتيمة وفق سياسة محددة.
6. تقديم للمراجعة مع حفظ نسخة البيانات المقدمة، وإظهار «يحتاج استكمالًا» وأسباب واضحة عند النقص. تعديل العنوان أو الملكية أو وجهة الدفع بعد الاعتماد يعيد مراجعة الحقل الحساس؛ لا يُوقف كل فرع بسبب تعديل فرع آخر.
7. يصبح الفرع صالحًا للتشغيل بعد الاعتماد واكتمال المتطلبات، ثم يشغله موظف مخول. نميز بين «معتمد» و«متصل» و«مفتوح حسب الساعات» و«متاح لاستقبال الطلبات».

حالات المراجعة: مسودة، مقدّم، قيد المراجعة، يحتاج استكمالًا، معتمد، مرفوض، معلّق، قيد الإغلاق، مغلق. حالة تشغيل مستقلة: غير متصل، متاح، مشغول، إيقاف مؤقت. خادم الطلبات وعرض المستخدم والسائق يطبّق الأهلية الموحدة، وليس الواجهة وحدها.

## 6. الأدوار والصلاحيات المقترحة

| الدور | الصلاحيات الافتراضية | القيود |
|---|---|---|
| المالك | نشاطه وعلاماته وفروعه وتفويض الموظفين وربط الأجهزة | نقل الملكية وتغيير وجهة الدفع والحذف بتحقق إضافي |
| مدير الفرع | تشغيل الفروع المعينة، الطلبات، القائمة والساعات | لا ملكية أو إغلاق نهائي أو منح صلاحيات أعلى منه؛ تفويض الموظفين إذن منفصل |
| الاستقبال | قبول/رفض الطلب حسب السياسة، حالات التحضير والتسليم، التوفر المؤقت | لا محفظة ولا مستندات المالك ولا إدارة مستخدمين |
| المالي | الرصيد والحركات والتقارير للفروع المعينة | التحويلات وطلبات الصرف صلاحيات منفصلة بحدود ومراجعة حيث يلزم |
| قارئ التقارير | قراءة التقارير المسموح بها | لا كتابة أو تشغيل أو نقل أموال |

التنفيذ يعتمد صلاحيات فعلية في الخادم، والأدوار قوالب سهلة للمالك. يمنع رفع الصلاحيات الذاتية وتفويض صلاحية لا يمتلكها المفوض. سحب الصلاحيات يرفع إصدار العضوية ويلغي الجلسات الخاصة فورًا، بما فيها الرموز الصادرة سابقًا؛ فصل الشخص من مطعم لا يحذف حسابه أو عضوياته الأخرى. دعوة الهاتف تتطلب قبولًا بعد إثبات الرقم، ولا يُكشف عبر البحث عن الهاتف ملف الشخص أو تفاصيل حساباته.

## 7. الجهاز المشترك والهاتف الشخصي

- «وضع جهاز الفرع» يُفعّل من مالك/مدير مخول باستخدام رمز ربط قصير العمر ولمرة واحدة. الجهاز لا يحتفظ بتوكن المالك كهوية تشغيل دائمة.
- جلسة استقبال مقيدة بفرع وجهاز؛ تنبيهات الطلبات بلا محفظة أو إدارة ملكية. تحديد ما يمكن فعله قبل فتح جلسة موظف: عرض وتنبيه فقط افتراضيًا؛ قبول الطلب يحتاج موظفًا مخولًا، مع دعم قبول آلي صريح إذا اختاره المالك.
- PIN فردي على الأجهزة المعتمدة فقط، يضبطه الموظف بعد تحقق قوي. مقترح أولي: 6 أرقام، قفل المهام الخاصة بعد دقيقتين من الخمول، إيقاف المحاولات بعد خمس محاولات فاشلة مع استعادة موثقة. القيم قابلة للضبط بعد الاختبار ولا تُعرض كمعيار قانوني.
- التحقق من PIN في الخادم، وتخزين اشتقاق مقاوم للتخمين مع ضوابط محاولات؛ لا PIN نصي أو تحقق محلي يكشف صلاحيات مالية دون خادم.
- قفل/خروج الموظف يبقي اتصال استقبال الفرع. خروج جهاز الفرع أو إلغاء اعتماده ينهي الاتصال ويغيّر حالة التوفر وفق سياسة تشغيل واضحة.
- المالية من الهاتف الشخصي تستخدم دخول الهاتف والصلاحيات نفسها. PIN التابلت لا يفتح حسابًا على هاتف جديد. تعديل بيانات الدفع/التحويلات الحساسة يحتاج تحققًا أقوى حسب سياسة المالية الحالية.
- Push وWebSocket يعالجان الحدث نفسه بمعرف موحد لمنع تكرار الصوت. الاستعادة تعيد مزامنة الطلبات وتكشف الصمت؛ Push وحده لا يثبت أن المطبخ جاهز. iOS لا يضمن اتصال WebSocket دائمًا في الخلفية.
- في انقطاع الشبكة لا نقبل كتابة مالية أو قبول طلب بوصفه ناجحًا دون إقرار الخادم؛ تعرض بيانات مخزنة بوقت آخر تحديث، وتمنع إعادة التنفيذ المكرر عند عودة الاتصال.

## 8. الشاشات المطلوبة

التطبيق: تسجيل الشخص والتحقق؛ «مطاعمي»؛ تفاصيل المطعم وفروعه؛ إضافة/استكمال الفرع؛ حالة المراجعة؛ الموظفون والدعوات والصلاحيات؛ أجهزتي/أجهزة الفروع؛ ربط جهاز؛ اختيار الموظف وPIN وقفل المهام؛ لوحة الفرع الحالية بعد اختيار واضح؛ المالية والتقارير حسب الدور.

المنصة المركزية: مراجعة الأشخاص عند الحاجة والأنشطة والفروع، أسباب الرفض/الاستكمال، إدارة التغطية، مراقبة الأجهزة والاتصال، سجل تغييرات الصلاحيات، سياسة الجلسات والمستندات، والتحقيق في أخطاء التفعيل. نستخدم صفحة Settings الحالية للسياسات المناسبة، مع سجل تدقيق واعتماد التغييرات الحساسة وفق النظام الموجود.

## 9. الربط مع حذف الحسابات

- حذف الشخص: تسوية ارتباطات الملكية أو نقلها أولًا، إزالة بياناته وعضوياته وجلساته وأجهزة الدخول، مع حماية السجلات اللازمة وفق السياسة المعتمدة. نقل الملكية لا ينفذ بتعديل ownerId منفرد.
- مغادرة الموظف: إزالة عضويته في النطاق المختار فقط، وإبطال جلسته على الأجهزة؛ استقبال الفرع يبقى إذا ظل الجهاز معتمدًا.
- إغلاق فرع: توقف الطلبات الجديدة، تسوية الطلبات والأموال، إزالة المنتجات الخاصة بالفرع وملفاته ورموز أجهزته؛ لا تحذف العلامة أو بيانات الفروع الشقيقة أو حساب المالك.
- إغلاق علامة/نشاط: جرد كل الفروع والملكية والمستندات والمشاركة قبل التنفيذ؛ الملفات المشتركة لا تحذف بسبب إغلاق فرع واحد.
- اكتمال حذف الشخص يُبطل رموزه ويزيل الكاش وينقله للدخول؛ اختبار الإقلاع البارد إلزامي لمنع ظهور حساب محذوف. العضوية المجددة لا تُلغى بإعادة تشغيل طلب مغادرة قديم.

| 2 — التسجيل ومساحة المالك | فصل إنشاء الشخص عن الفرع، مسودات، مطاعمي، إضافة عدة علامات وفروع، مراجعة مركزية | حساب واحد يضيف فرعين؛ فرع pending لا يمنع الوصول إلى الفرع المعتمد ولا يظهر كجاهز للطلب |
| 3 — الموظفون والمالية | دعوة وقبول ونطاق وتعديل وسحب، ترحيل الصلاحيات المالية الموجودة دون توسيعها، الهاتف الشخصي | السحب يمنع API فورًا ويبقي حساب الموظف وعضوياته الأخرى |
| 4 — جهاز الفرع وPIN | ربط وإلغاء جهاز، جلسات استقبال/موظف منفصلة، ضوابط PIN، قفل وتبديل، معالجة الصوت والتزامن | قفل المالية لا يوقف استقبال طلب حقيقي؛ لا تسرب بيانات مالية ولا قبول مزدوج |
| 5 — تكامل التطبيقات والحذف | أهلية العرض في المستخدم والتوجيه للسائق، branchId، القوائم والمناطق والمحافظ، توسيع عامل الحذف لكل روابط جديدة | إغلاق فرع لا يؤثر على الشقيق؛ حذف الشخص لا يسمح باستعادة جلسة قديمة |
| 6 — إطلاق تدريجي | أعلام ميزات ثم تجربة فرعين وموظفين على Staging؛ مراقبة ثم تفعيل مجموعة محدودة قبل التعميم | جميع معايير القبول أدناه مكتملة، وخطة استرجاع مجربة |

لا ننشر كل المراحل دفعة واحدة. تقدير المدة والملفات النهائية يصدر بعد المرحلة 0، بدل إعطاء وعد زمني قبل حصر الاعتماديات.

## 11. ترحيل البيانات والاسترجاع

نبدأ بتقرير قراءة فقط: حسابات وأعمال ومالكون وصلاحيات مالية وحالات حذف. لكل businessId حي: إنشاء روابط نشاط وعلامة وفرع متوافقة مع البيانات؛ اختلاف الهاتف وحده لا يبرر دمج ملكية. الحسابات المحذوفة وأعمالها لا تُعاد إلى الحياة. المطاعم المعلقة لا تعتمد تلقائيًا، والغموض يذهب للمراجعة.

ترحيل قابل لإعادة التشغيل ومشروط بالإصدار، مع عدادات قبل/بعد ومطابقة إجماليات المحافظ وعدد الطلبات ومعرفاتها. لا نغير ledger أو مبالغ الأموال أثناء ترحيل الصلاحيات. القراءة تتوافق مؤقتًا مع السجلات القديمة؛ الكتابة الجديدة في مصدر واحد، وأي كتابة مزدوجة تحتاج تسوية ومراقبة محددتين.

الاسترجاع يعطل واجهات الإنشاء/الربط الجديدة بأعلام الميزات، ويحافظ على guards الأمنية؛ لا نعود إلى نسخة تمنح صلاحية مسحوبة. لا نحذف البيانات القديمة حتى تنتهي المطابقة. استرجاع النسخ الاحتياطية يطبق سجل الحذف وإبطال الصلاحيات، ولا يعيد حسابات محذوفة.

## 12. اختبارات القبول الكاملة

1. شخص واحد: البركة — المناذرة والمشخاب، ومطعم باسم آخر؛ اختيار صحيح بلا الاعتماد على أول سجل.
2. OTP وتطبيع 07 و+964، رقم مكرر، انتهاء وإعادة إرسال وحدود محاولات؛ المسودة لا تمنح ملكية دون تحقق.
3. فرع pending وشقيق approved؛ رفض نقص الوثائق وتصحيحه؛ عدم إنشاء طلب لغير المؤهل عبر API حتى لو تغيرت الواجهة.
4. موظف استقبال فرع واحد، مدير فرعين، مالي للاثنين بلا تحويل ثم منحه ضمن الحد؛ تجاوز API ونطاق الفرع مرفوض.
5. دعوة منتهية/ملغاة/مكررة ورقم غير المقصود، تزامن قبول وسحب، تغيير إصدار العضوية أثناء التنفيذ.
6. الجهاز المشترك: قفل المالي وتبديل الموظف؛ وصول طلب حقيقي بصوت واحد في المقدمة والخلفية؛ ربط جهاز غير مصرح وإلغاء جهاز مستخدم.
7. هاتف الموظف المالي لا يستطيع الفرع غير المعين؛ سحب الصلاحيات مع تطبيق مفتوح ورمز صالح سابقًا يمنع العملية.
8. طلب يصل لجهازين: قبول/رفض متزامن لا ينفذ مرتين؛ التحويل يتكرر بعد timeout لا ينشئ خصمًا ثانيًا.
9. انقطاع الإنترنت/إعادة تشغيل/قتل التطبيق وانتهاء الجلسة؛ بيانات الفرع المخزنة لا تظهر لحساب آخر ولا تعرض نجاحًا وهميًا.
10. مغادرة عضو مع فروع أخرى، إغلاق فرع له شقيق، حذف مالك مع نقل أو ملكية قائمة، ملفات مشتركة، إكمال الحذف وتسجيل الخروج والإقلاع البارد.
11. ترحيل ثم إعادة تشغيل الترحيل ثم استرجاع: نفس المعرفات والأرصدة والطلبات، بلا صلاحيات إضافية أو حسابات محذوفة عائدة.
12. مراجعة موظف المنصة غير المخول، سجل تدقيق بلا OTP/PIN/tokens، مستندات خاصة وروابط منتهية، العربية RTL والأسماء الطويلة وسهولة الاستخدام.

## 13. تعريف اكتمال التحديث

يكتمل عندما يعمل التسجيل المستقل وإضافة عدة مطاعم وفروع ومراجعتها وتفويض الموظفين وسحبهم والجهاز المشترك والهاتف الشخصي، وتنجح اختبارات الطلبات والمحافظ والحذف والترحيل والتزامن والانقطاع. لكل مسار إذن خادمي مثبت وسجل تدقيق، وتوجد سياسة تشغيل للمستندات والجهاز والتفعيل. لا يكفي ظهور الشاشات لإعلان اكتمال التحديث.

المستندات المطلوبة محليًا وقبول المطابخ المنزلية واتفاقية الشراكة ووجهة التسويات تحتاج اعتمادًا تشغيليًا محليًا قبل الإطلاق؛ يمكن تجهيزها كإعدادات ومراجعة دون اختراع متطلبات عراقية. لا نمنح تحويلات لجميع الماليين تلقائيًا، ولا ننقل الملكية تلقائيًا ضمن هذه الخطة.
