# فحص وخطة حذف الحسابات — Staging

تاريخ الفحص الأول: 2026-10-13. الأقسام الأولى نتائج تاريخية قبل التنفيذ؛ راجع تحديث 2026-10-14 في نهاية الوثيقة والحالة التشغيلية الحالية في account-deletion-retention-operations.md.

## النتائج المثبتة

- المستخدم: `frontend/lib/screens/delete_account_screen.dart` يحاكي انتظارًا ثم يسجّل الخروج ويعرض نجاحًا دون API. `AuthService.deleteAccount` يعيد نجاحًا دون عملية حذف. الشاشة تطلب كلمة مرور رغم اعتماد الهاتف.
- السائق: توجد واجهة حذف في تفاصيل الحساب، لكنها تتصل بعنوان `https://your-backend-url.com/api/v1/driver/account` وتطلب كلمة مرور وسببًا إلزاميًا. لا يوجد معالج حذف في ملف خادم السائق الحالي. API المنشور يستخدم proxy؛ وجود proxy ليس دليلًا على تنفيذ مسار الحذف.
- المطعم: يوجد معالج حقيقي `delete_business_handler.js`، وتأكد تطابقه مع دالة Staging المنشورة `order-receiver-regional-staging-delete-business-v1-sam`. يربط حذف المطعم بحذف مستخدم المالك وحسابه في Cognito؛ لا يفحص ملكية مطاعم أخرى أو الطلبات أو المحافظ أو الموظفين. تأكيد كلمة المرور اختياري. يوجد fallback إلى `jwt.decode` عند فشل تحقق Cognito؛ يجب إزالته واستبداله بتحقق يفشل بأمان، بصرف النظر عن طبقة API Gateway. يسجل الطلب الكامل بما قد يتضمن token وكلمة مرور. الاستعلام عن المنتجات والخصومات يستخدم Query دون KeyConditionExpression ويتجاهل الخطأ بإرجاع قائمة فارغة، ولا يعالج pagination. يتجاهل بعض أخطاء الحذف ويستطيع عرض نجاح مع بقايا بيانات. لا ينظف كل ارتباطات المطعم. النص في التطبيق يعد بحذف الطلبات بينما المعالج لا يحذفها.
- المنصة: خدمة الموظفين تدعم ACTIVE وSUSPENDED وتغييرات صلاحيات مع اعتماد مستقل وسجل تدقيق وإلغاء جلسات. لا يظهر مسار كامل لإنهاء حساب موظف وحذف بياناته الشخصية. تعليق الموظف ليس حذفًا نهائيًا.
- المحافظ: توجد حالات ACTIVE/SUSPENDED/CLOSED، وتمنع التحويلات لمحفظة غير ACTIVE. يجب تصميم التسوية قبل الإغلاق؛ تعليق جميع العمليات مباشرة قد يمنع رد الأموال. محافظ المستخدم والسائق مرتبطة بمعرفيهما؛ محفظة المطعم مرتبطة بالمطعم، لا بالموظف المالي.

## السياسة حسب التطبيق

### المستخدم
طلب حذف الحساب الشخصي مع OTP للرقم الموثق وسبب اختياري. يشمل الملف والعناوين والمفضلة وبيانات الأجهزة والإشعارات والملفات المرفوعة والبيانات المرتبطة بالحساب بحسب الحصر. الطلبات الجارية والتحويلات والمبالغ تبقى قابلة للتسوية؛ لا نعد بفقدان الأموال أو إزالة كل الطلبات التاريخية. يحتفظ فقط بما يلزم بموجب سياسة احتفاظ محددة. يدعم الحسابات القديمة ذات userId مختلف عن Cognito sub دون ربط اعتمادًا على رقم أو بريد يرسله العميل.

### السائق
ثلاث عمليات مستقلة: إيقاف استقبال الطلبات مؤقتًا، تعليق إداري مع السبب ومسار مراجعة، حذف يطلبه السائق. الحذف يوقف التعيينات الجديدة بعد قبول الطلب، ويتيح إنهاء أو إعادة إسناد الرحلة الجارية وتسوية الحجوزات والأرباح والرصيد. ثم يحذف بيانات الملف والمركبة والموقع والأجهزة والوثائق غير المطلوبة للاحتفاظ. لا تُمحى الحركات المالية ولا ينشأ رصيد بديل. التسجيل لاحقًا يحتاج إجراءات اعتماد السائق مجددًا؛ لا تستخدم سياسة الحذف للتحايل على الحظر أو الاحتفاظ ببيانات غير لازمة.

### المطعم وموظفوه
فصل إغلاق/حذف المطعم عن حذف حساب شخص. صاحب المطعم فقط يطلب إغلاق المطعم؛ الموظف المالي لا يملك هذا الحق لمجرد صلاحيات التحويل. إيقاف الطلبات الجديدة وتسوية الحالية والمحفظة والحملات والصلاحيات وروابط المنتجات. حذف المطعم لا يحذف كتالوج المنتجات العالمي أو حساب المالك الذي يدير مطاعم أخرى. الموظف يحذف حسابه الشخصي أو يغادر عضوية المطعم دون حذف المنشأة أو محفظتها. المالك الذي يطلب حذف حسابه مع مطاعم قائمة يرى خيار نقل الملكية بتحقق من الطرفين أو إغلاق المنشآت؛ لا تُترك منشأة بلا مالك. تُفصل المغادرة وإلغاء العضوية عن حذف الحساب النهائي.

### موظفو المنصة
إنهاء وصول الموظف عملية إدارية مع اعتماد مستقل عند الحاجة: إزالة الأدوار وتعليق/إغلاق الهوية وإلغاء الجلسات والدعوات والتحقق من الأعمال المعلقة. تُحفظ إسنادات الموافقات والتدقيق بالقدر اللازم، مع إزالة بيانات الاتصال غير اللازمة. طلب محو البيانات الشخصية مسار منفصل عن إيقاف الوصول. حماية آخر مدير فعلي وآخر معتمد لازم للتشغيل عبر نقل المسؤولية أولًا، وليس رفض الحذف بلا حل. موظف المنصة لا يحذف محفظة المنصة أو بيانات العملاء أثناء حذف حسابه.

## البنية المشتركة

1. حصر الجداول وGSIs وS3 والمواقع وFCM/APNs والإشعارات وCognito والبيانات الخارجية ونسخ الاحتياط لكل هوية. يصنف كل مورد: حذف، إزالة ارتباط، احتفاظ مع السبب، أو تسوية. يشمل هويات الضيوف إن كانت تُنشأ على الخادم.
2. سجل طلب مستقل ومعرف idempotency يمنع التنفيذ المكرر. حالات مقترحة: REQUESTED، VERIFYING، PENDING_SETTLEMENT، READY، PROCESSING، COMPLETED، RETRY_REQUIRED. فصل إعادة المحاولة التقنية عن انتظار التسوية. إن أردنا فترة تراجع نضيف سياسة وحالة واضحة؛ لا نعتبر تسجيل الدخول وحده إلغاءً تلقائيًا.
3. المصادقة من token متحقق منه ومن pool/client الصحيحين، وليس userId في الطلب. OTP للحذف له purpose خاص ويرتبط بالهوية والطلب والنطاق، بصلاحية محدودة واستخدام واحد وحدود إرسال ومحاولات. لا يقبل OTP الدخول أو التحويل بديلًا عنه. موظفو المنصة يستخدمون تحقق MFA مناسبًا لطريقتهم الحالية.
4. الطلب يقبل ويعرض حالته حتى عند وجود مستحقات. يوضح العنصر الذي يحتاج تسوية ومسار الحل دون تعليق الطلب بلا موعد أو متابعة. لا يصفر الرصيد ولا يسقط حق المستخدم. إضافة مسار رد/سحب موثق عند عدم وجوده شرط لإكمال الحذف المالي.
5. بعد قبول الطلب: منع الأعمال الجديدة غير المناسبة مع إبقاء وصول محدود للحالة والتسوية. جميع خدمات الطلبات والمحافظ وتعيين السائقين والصلاحيات يجب أن تطبق حالة الحساب؛ واجهة التطبيق أو تعطيل Cognito وحدهما لا يمنعان كل token صادر سابقًا. العمليات المتزامنة تحتاج checks مشروطة وإصدارات، مع ترتيب منسق بين الخدمات.
6. عامل تنفيذ قابل للاستئناف يسجل نجاح كل خطوة ويعيد الفاشل فقط. لا تستخدم DynamoDB TTL لإثبات اكتمال الحذف. إزالة البيانات الشخصية والملفات ثم إغلاق الهوية في ترتيب يمنع الدخول أثناء التنفيذ دون فقدان حق التسوية. تحديث الإشعارات وروابط العضوية ومحركات البحث/التقارير المتأثرة.
7. إغلاق المحفظة بعد التسوية دون حذف ledger. استخدام معرف داخلي محدود في السجلات المحتفظ بها لا يجعلها مجهولة الهوية تلقائيًا. إزالة الهاتف والاسم والعنوان من نسخ الطلبات حيث لا يلزم الاحتفاظ بها، لا من جدول الملف وحده.
8. حذف الأجهزة والتوكنات وكاش التطبيق وتسجيل الخروج بعد استجابة موثقة. رسالة تقديم الطلب تختلف عن اكتمال الحذف. تأكيد اكتمال على الشاشة أو قناة مسموحة قبل إزالة بيانات الاتصال.
9. النسخ الاحتياطية لها مدة انتهاء معلنة، وعمليات الاستعادة تطبق سجل الحذف حتى لا تعيد تنشيط الحساب أو بياناته المحذوفة. أي سجل منع إعادة إنشاء أو مكافحة إساءة استخدام يحتاج نطاقًا وسببًا ومدة، لا احتفاظًا مفتوحًا.

## الإعدادات والإدارة

إعدادات موثقة ومؤرخة: مهلة التراجع إن اختيرت، مدة المعالجة المستهدفة، حدود OTP، إعادة المحاولة، مدة الاحتفاظ لكل فئة وسببها. لا يُسمح بتقليل مدة إلزامية أو تغيير سياسة منشورة بصمت. التغييرات الحساسة تعتمد من شخص مستقل وتسجل في التدقيق، وتحدد النسخة التي تسري على الطلبات القائمة. لم تُحسم مدد الاحتفاظ القانونية؛ لا نفترض مدة Uber مناسبة لنا ولا نفعّل حذفًا نهائيًا مجدولًا قبل تحديدها.

صفحة المنصة تعرض طلبات الحذف، التطبيق والنطاق والحالة والعوائق والتقدم والفشل. صلاحيات مشاهدة محدودة، ومراجعة التسوية للمالية، وقرارات المطعم للتشغيل/المالك، وإدارة الموظفين حسب الصلاحيات. المشرف لا يعدل الرصيد لتجاوز شرط الحذف، ولا يطلب OTP المستخدم أو يتجاوز تحقق هويته.

## ترتيب التنفيذ

1. إزالة رسائل نجاح المستخدم الوهمية وتأمين معالج المطعم القديم لمنع مسار حذف ناقص أو غير متحقق من الهوية. إجراء تحديث منفصل قابل للمراجعة، مع تجنب تعطيل خدمة مشروعة بلا بديل محدد.
2. حصر البيانات واعتماد سياسة النطاق والاحتفاظ وتسوية الأموال. تجهيز خطة ترحيل للحسابات القديمة والموظفين ومتعدد المطاعم.
3. بناء طبقة طلب الحذف والتحقق والتنسيق والتنفيذ والتدقيق والإعدادات وصفحة المتابعة على Staging.
4. المستخدم أولًا، ثم السائق، ثم المطعم والعضويات والملكية، ثم إنهاء حساب موظف المنصة. كل مرحلة تختبر وتراجع قبل التالية.
5. تحديث الشاشات والسياسة والروابط العامة لطلب الحذف للمتاجر. ألوان التطبيق المعتادة مع لون تحذير محدود، دون شاشة حمراء كاملة. أسباب المغادرة اختيارية، والأزرار تمنع تكرار الطلب وتعرض الحالة الحقيقية.
6. اختبارات آلية وتكامل على هويات تجريبية مخصصة فقط، ثم اختبار يدوي. لا تستخدم الحسابات الحالية ذات أرصدة لحذف تجريبي. النشر يبقى Staging حتى اعتماد النتائج والسياسة.

## شروط النجاح والاختبارات

- طلب مكرر أو شبكة منقطعة لا يسبب حذفًا مزدوجًا أو نجاحًا وهميًا.
- token مزور/منتهي أو من تطبيق آخر وOTP خاطئ/منتهي/مكرر لا يمنح حق الحذف.
- سباق حذف/تحويل أو حذف/قبول طلب يمنع إنشاء عمل جديد بعد نقطة المنع المحددة، ويحفظ الحجوزات والمستحقات.
- حساب بلا رصيد يكتمل، وحساب برصيد أو حجز أو طلب نشط يدخل تسوية واضحة.
- فشل S3/DynamoDB/Cognito يظل مسجلًا ويستأنف؛ لا يختفي من لوحة الإدارة.
- حذف موظف مطعم لا يؤثر على مالكه؛ حذف مطعم لا يؤثر على مطاعم أخرى أو المنتجات المشتركة.
- تعطيل موظف يسحب صلاحياته من الخدمات الفعلية، مع حفظ سلامة سجل الموافقات.
- تنظيف الحساب القديم يشمل userId المحلي وCognito sub الصحيحين، دون حذف حساب آخر له رقم مشابه.
- الاستعادة من backup لا تعيد حسابًا محذوفًا، والكاش والأجهزة الأخرى لا تعرض بياناته بعد إبطالها.

## سجل بدء التنفيذ

- أزيل نجاح الحذف الوهمي من كود المستخدم المحلي؛ لا توجد خدمة حذف جديدة مربوطة بالواجهة بعد.
- عُطّل تنفيذ الحذف القديم للمطعم على Staging باستجابة authenticated fail-closed لا تحذف بيانات. أزيل fallback قراءة JWT غير المتحقق منه وتسجيل الطلب الكامل. نجحت 4 اختبارات لهذا الحاجز.
- أضيف منطق سياسة ومنسق حذف مشترك في `backend/account-deletion`، مع 22 اختبارًا ناجحًا للهوية والنطاق والتسوية والطلبات المكررة وإعادة محاولة التنظيف. هذا أساس برمجي وليس API منشورًا.
- بدأ حصر موارد AWS: محافظ المستخدم الأساسية ومحافظ دفع الطلبات منفصلتان، ويلزم فحص كلتيهما. طلبات التطبيقات مرتبطة بجدول WizzOrders، وبيانات المستخدم القديمة قد تستخدم userId مختلفًا عن Cognito sub.
- التوصيلات الفعلية لمخزن الطلبات وSMS والعامل وواجهات التطبيقات ما زالت قيد التنفيذ. طريقة رد الأموال ومدد الاحتفاظ لم تُحسم، ولا يوجد حذف آلي نهائي مفعل.

## توجيه صاحب المشروع — تسوية الرصيد وسياسة الاحتفاظ

طرق التسوية التي حددها صاحب المشروع:

1. تحويل الرصيد إلى محفظة أخرى يختارها صاحب الحساب، عبر مسار التحويل المتحقق والموثق. تظل حدود التحويل والحجوزات سارية؛ لا توجد صلاحية لتجاوزها بمجرد طلب الحذف.
2. طلب صرف عبر زين كاش تنفذه الإدارة على رقم الحساب الموثق أو رقم آخر يدخله صاحبه. يسجل الرقم المقصود والمبلغ ويؤكد صاحب الحساب الطلب بتحقق مستقل؛ إثبات كون الرقم محفظة زين كاش ليس نتيجة OTP وحده. الصرف غير آلي ما دام التكامل المباشر غير موجود. يُنشأ طلب مالي يحتاج منشئًا ومعتمدًا مستقلًا ومرجعًا/إثباتًا للدفع. لا يخفض الرصيد عند تقديم الطلب أو اعتماده وحدهما، بل وفق تنفيذ تسوية موثوق يمنع التكرار ويتعامل مع فشل التنفيذ والمصالحة. الرصيد المطلوب صرفه يحتاج حجزًا أو مانع إنفاق متزامن، ولا يصبح قابلًا للصرف والتحويل في آن واحد.

صاحب المشروع أكد عدم وجود سياسة احتفاظ معتمدة حاليًا، وطلب معرفة الممارسات المعتادة. لذلك لا توجد مدة جديدة معتمدة أو purge مجدول مفعل.

مسودة السياسة المقترحة للنقاش:
- الحساب والوصول والعناوين والمفضلة والتوكنات والبيانات الشخصية غير اللازمة: يبدأ حذفها فور تحقق الشروط؛ لا فترة تراجع إلزامية.
- قيود الرصيد والتحويل والتسوية والفواتير: يحتفظ بالحد الأدنى اللازم في أرشيف محدود الوصول. 7 سنوات خيار للمراجعة وليس مدة قانونية محسومة لمنصتنا؛ يلزم تحديد الأساس وبداية احتساب المدة ونطاق البيانات قبل الاعتماد.
- الطلب المكتمل: فصل بياناته المالية عن الاسم والهاتف والعنوان الدقيق؛ إزالة البيانات الشخصية عندما تنتهي الحاجة التشغيلية المشروعة، مع إبقاء المرجع المالي المحدود.
- بيانات الموقع والوثائق والصور والمحادثات: لا تدخل تلقائيًا في احتفاظ مالي طويل؛ لكل فئة مدة محددة وسبب، مع احتفاظ استثنائي لواقعة أو مطالبة قائمة فقط.
- النسخ الاحتياطية: مدة انتهاء محددة بحسب إعدادات النسخ الفعلية، ويطبق سجل الحذف عند الاستعادة. لا تُعد محذوفة من النسخ قبل انتهائها.
- التحقيقات والنزاعات: احتفاظ محدود بالبيانات ذات الصلة، مع مراجعة وموعد انتهاء، وليس استثناءً مفتوحًا لكل بيانات الحساب.
