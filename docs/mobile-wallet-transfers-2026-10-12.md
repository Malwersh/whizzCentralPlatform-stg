# Mobile wallet transfers — Staging

The driver, customer and merchant applications use solid brand-primary and brand-secondary colors, neutral surfaces and a consistent recipient/amount/reason/confirmation flow. No gradients are introduced.

## Source of truth

`/wallet/transfers/context` returns authenticated-account balance, availability, per-transfer limits and Baghdad-day usage from the centralized wallet service. Recipient lookup is by exact Iraqi phone number and explicit driver/customer type; no full recipient directory is exposed. `/history` scopes its query and cursor to the caller's wallet. `/status` can only read that principal's outgoing transfer.

Customer transfer accounts start at zero, separately from the existing checkout-wallet service. The customer UI labels this distinction. No legacy balances are imported and no checkout or legacy payment endpoints are changed. Merchant wallets are scoped to the stored business owner; a separate explicit grant enables a merchant financial employee. Existing order-management membership does not grant financial access. A merchant-only account list lets delegated employees open their assigned wallets without owning a restaurant; no order-management access is added. Mobile transfer endpoints also validate the live Cognito access session to reject signed tokens from disabled or revoked sessions. Merchant owners assign/revoke registered merchant accounts by verified email or phone, with recent authentication and audit. A monetary transaction condition-checks the current ownership and enabled grant version, so revoked access cannot use a stale screen.

Merchant outgoing daily limits are editable through central financial settings, subject to independent approval. Existing settings without a merchant-specific limit inherit the driver daily limit. Mobile limits are enforced again by the atomic server-side transaction; the UI is advisory.

## Interrupted requests

The application persists the transfer UUID and payload per wallet before submission. After reopening, it queries the same operation before retrying. Cancellation of an uncertain attempt atomically writes a CANCELLED tombstone only if no transfer exists; if a monetary commit won the race, the server returns its committed result. No new UUID is silently generated for an unknown outcome.

## Proxy authorization correction

Interactive simulator testing exposed a denial before the wallet handler: the REST API proxy reports `ANY` to the authorizer, while the explicit mobile permission map uses GET/POST. The authorizer now accepts the union of the defined GET/POST roles only for each known mobile transfer path. Unknown paths and merchant-only paths remain denied for other account types. The handler rejects unsupported mobile transfer methods with 405 rather than falling through to generic wallet handling. Live session, ownership and financial-grant checks remain enforced.

Both Staging Lambda code updates completed successfully. All 77 backend tests and 7 authorizer tests passed, including the proxy-method regression test. Interactive retry in the customer and merchant simulators is pending confirmation; no balances were adjusted for this correction.

## In-screen transfer verification and wallet entry improvements

Staging mobile transfers can satisfy the configured recent-authentication requirement with a phone OTP instead of signing out. The live Cognito account must own a verified Iraqi phone. Confirmation binds the principal, source wallet, request UUID, recipient wallet, amount and normalized reason. HMAC-only code storage, five-minute expiry, five attempts, resend cooldown and send quotas are enforced on the server. A verified confirmation is consumed in the same DynamoDB transaction as the balances and ledger. It cannot authorize another transfer, and its validity is also constrained by current financial reauthentication settings. Finance staff maker/checker authentication remains unchanged.

The client preserves the same transfer UUID, opens an OTP sheet on REAUTH_REQUIRED, and retries the same operation after verification. Retrying a successful OTP verification after a lost response returns the same proof only after checking the same valid code and identity. Cancellation still requires the server tombstone before forgetting an uncertain operation.

The customer home wallet tab opens the centralized transfer wallet directly. The live authorizer phone status replaces the enrollment button with the verified number when available. The legacy checkout balance remains separate and is explained in the wallet. The driver transfer action sits inside the balance card and refreshes the balance after returning.

Validation: 83 backend tests, 8 authorizer tests, two driver widget tests (interrupted transfer and in-screen verification), and targeted analysis passed. An isolated DynamoDB table tested the send/cooldown/incorrect-code/verify/response-loss retry/payload binding/one-time consumption path with fake SMS; the table was deleted. Staging backend deployment completed. Driver Release was installed/launched on the real device; customer and merchant simulator builds were installed/launched. Actual SMS delivery and a transfer through the new sheet remain interactive checks. No operational test money was moved by these checks.

Completed/cancelled references still return their scoped existing result without a new OTP or duplicate debit. The backend regression suite passes 84 tests, including fresh-session rejection without confirmation.
