# الجزء 266 — مراجعة النقد ورد أموال الزبون

وافق المستخدم على قواعد المعالجة بعبارة «تمام جيد طبقها» بعد شرح فصل التحصيل، ومسؤولية الفرق، ومصدر الرد. التنفيذ مخصص لـstaging والطلبات المالية المثبتة مسبقًا، ولا يعيد فتح القضية التاريخية أو إقرارها أو صرفها.

## السلوك

- إفادة الزبون أو السائق بالمبلغ المدفوع بلاغ موثق من حسابه الأصلي، وليست وحدها إثبات تحصيل أو مسؤولية مالية. المطابقة تتطلب آخر إفادتين متفقتين، ومراجعة موظف مخول. لا يؤدي اختيار أمين صندوق إلى منحه صلاحيات مالية.
- عند ظهور خلاف تحصيل قبل التسوية، يمنع `openPaymentClaimId` تسجيل دفع كامل أو مرتجع بلا نقد. الشرط محفوظ داخل معاملة التسوية/المرتجع نفسها، بما يمنع سباق فتح الشكوى مع الصرف. يظل إكمال المهمة المالي للمراجعة؛ لا نختلق تحصيلًا كاملًا أو إرجاع أصناف.
- إذا استكمل الزبون المبلغ فعلًا، تسجل إفادتان جديدتان، ثم مطابقة وإغلاق بلا تعديل مالي، وبعده يمكن تنفيذ تسوية الطلب الأصلية بسعره المقبول. المبلغ الناقص لا يُحمّل تلقائيًا للسائق أو المطعم.
- القرار بشأن الفرق يسجل مسار متابعة التحصيل، أو مراجعة تحمل الشركة، أو مسؤولية السائق بأدلة، أو تعديل مستحق الطلب. هذه قرارات `PENDING_SEPARATE_EXECUTION`؛ ليست مصروف شركة منفذًا أو خصمًا على المحفظة. التسويات المعدلة لهذه المسارات ليست مكتملة ضمن هذا الجزء.
- يوجد سجل مراجعة نقد واحد لكل طلب، وقد يتضمن عدة ردود؛ يحجز مجموع جميع الردود المعتمدة والمنفذة، ويمنع تجاوز المحصل المثبت. الرد المنفذ يستهلك الحد حتى لو لم يؤكد الزبون الاستلام. التعويض الإضافي ليس ردًا من المبلغ المحصل ولا يُنفذ بهذه الواجهة.
- المصدر إما نقد غير مسوّى بعهدة السائق، أو صندوق شركة نشط للأموال المسوّاة. وجود النقد في جيب السائق لا يجعله غير مسوّى إذا سُجل قيد الطلب. يدعم الحد الفصل بين مبلغ مسوّى وزيادة غير مسوّاة في الطلب نفسه.
- المصدر الإلكتروني غير مفعّل هنا؛ يتطلب حسابًا تشغيليًا مسجلًا ومصدر تنفيذ يمكن مطابقته. لا يُقبل اسم محفظة أو مرجع حوالة حر بدل ربط الحساب.
- يولّد الخادم سند `CRV` ثابتًا لكل رد، بتقويم العراق. مراحل الرد: اعتماد وحجز، تنفيذ فعلي من السائق أو أمين الصندوق، إقرار الزبون الأصلي، مطابقة مالية، ثم إغلاق عند اكتمال القيود وعدم بقاء خلاف.
- تنفيذ الصندوق يخصم رصيده مرة واحدة، ويحفظ اسم الصندوق وأمينه وقت التسليم وسلسلة قيوده، بقيد متوازن `CUSTOMER_REFUND_EXPENSE / CASHBOX_ASSET`. استرداد المبلغ من المسؤول يحتاج قرارًا مستقلًا؛ لا يستعمل حساب صرف المطاعم أو محفظة المنصة.
- الصلاحية الحالية وحد المبلغ لازمان للاعتماد. يحتفظ التنفيذ بشروط صلاحية المعتمِد، ويفشل إذا تغيرت قبل التسليم. التنفيذ يحتاج أمين المصدر نفسه وصلاحية `finance.request` للنقد المؤسسي. لا يُشترط موظف ثانٍ إن كان الحساب نفسه مخولًا بالاعتماد والتنفيذ.
- الإلغاء مسموح للاعتماد الذي لم يُنفذ فقط. تعذر استلام الإقرار لا يعكس النقد الخارج أو يسمح برد ثانٍ. تغيير الإفادات يوقف التنفيذ المعلق، مع السماح بإلغائه للمراجعة.

## حفظ السجلات عند حذف الحساب

تُدرج القضية وأحداثها وسند رد السائق ضمن السجلات المالية ذات الإصدار4. تمنع المراجعة غير المنتهية حذف الحساب قبل حسمها. بعد الإغلاق تحفظ آلية الأرشفة الحالية المبالغ وأرقام السندات ومراجع القيود وتواريخ الإقرار والمطابقة وبصمات الإثبات خلال مدة الاحتفاظ المعتمدة؛ تُستبعد نصوص الشكاوى والهواتف والأسماء الشخصية وخرائط صلاحيات الموظفين من نسخة الأرشيف المالي. لا تُنشأ مدة احتفاظ أو صلاحية جديدة.

## الربط

المصنع `customerCashCase.ts` يحفظ السجل والأحداث والتدقيق وفهرس المراجعة وقيد المصدر/الصندوق في معاملة شرطية واحدة. يعاد التحقق من الهوية قبل المعاملة. يحافظ الفهرس ومراقب المهل على مراجعة النقد دون إجراء مالي تلقائي.

تختار إجراءات الخادم `customer_cash_case / driver_cash_case / staff_cash_case` مجمع Cognito؛ لا يختاره العميل. يستخدم مسار الزبون مورد POST الموجود ببروتوكول `CUSTOMER_CASH_REVIEW` قبل أي إجراء إلغاء. مسار السائق `/driver/orders/{id}/cash-review`. الإدارة تستخدم مورد إجراءات القضايا الحالي وصفحة `customer-cash-review.html`؛ تنتقل إليها قائمة القضايا مباشرة.

في المحاكي: الزبون 215 Debug والسائق 216 Debug. يوجد مدخل من تتبع طلب الزبون، وتسليم الطلب عند السائق وسجل رحلاته. لا يعني تثبيت المحاكي تحديث التطبيق على جهاز فعلي أو المتجر.

## التحقق والحدود

تغطي الاختبارات تجاوز المحصل، وحجز الردود المتزامن، وفقد استجابة الشبكة، وتغيير المصدر/الإفادات/صلاحية المعتمِد، وإقرار الزبون الصحيح، ومطابقة القيد، وإغلاق الردود المسوّاة، ومنع دفع كامل أثناء خلاف نشأ بعد القراءة. تختبر الحزمة المرشحة نفسها وسياج rollout مع هويات أصلية محاكية. تختبر واجهات Flutter جلسة الدخول والتأكيد الصريح وإعادة المحاولة، وصفحة الإدارة عرض الهاتف والصلاحيات وتحييد نصوص الأدلة.

كل التنفيذ المالي في الاختبارات داخل ذاكرة معزولة. الفحص الحي للطلب القديم للقراءة فقط، مع حظر كل الكتابات. لا فتح شكوى أو اعتماد أو تسليم نقد أو إقرار زبون حقيقي بواسطة الوكيل. الاختبار البشري لمسار رد جديد لم يُنفذ. اختبار موظف المطعم المالي يبقى مؤجلًا بطلب المستخدم.

هذا الجزء لا يكمل جميع سيناريوهات 244 أو التصحيح المالي بعد تحميل مسؤولية جديدة؛ خصوصًا تحمّل الشركة للفرق وتعديل مستحق الطلب وخصم المسؤول تحتاج تسوية مترابطة مستقلة، دون إعادة تشغيل صرف سابق.
