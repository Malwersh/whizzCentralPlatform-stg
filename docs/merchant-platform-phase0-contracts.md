## هوية ونطاق ثابتان

businessId الحالي = branchId التشغيلي أثناء الانتقال. نضيف organizationId وbrandId، ولا نعيد ترقيم المحفظة أو الطلب أو ندمج الفروع بسبب اشتراك الهاتف. عضوية ذات membershipId وsubjectId وversion وbranchIds وstatus؛ فهرس subject لا email. جهاز معتمد branchId/deviceId/version، جلسة موظف تربط معرف وإصدار العضوية والجهاز والفرع ومدة. سحب العضوية/الجهاز يبطل جلسة قديمة حتى لو لم تنتهِ.

الموظف المالي يقرأ افتراضيًا؛ التحويل والصرف صلاحيات منفصلة تخضع للنظام الحالي. لا يورث جهاز استقبال الطلبات دور المالك. قالب الدور ليس بديلًا عن شرط الخادم ومعاملات منع التزامن.

## API الجديدة المقترحة قبل تثبيت أسماء نشرها

- تسجيل شخص هاتف موثق + ملف شخص مستقل؛ GET مساحة الأعمال دون فرع افتراضي.
- POST/PATCH مسودات نشاط/علامة/فرع، POST تقديم؛ reviewStatus منفصل عن operatingStatus.
- GET/POST/PATCH أعضاء ودعوات ضمن نشاط وفروع؛ قبول هاتف وإلغاء بإصدار.
- ربط/إلغاء جهاز وإصدار جلسة استقبال محدودة، فتح جلسة موظف PIN وإقفالها مستقلة.
- أقسام/منتجات/خيارات ومسودات قائمة بإصدار، نشر ومعاينة؛ quote خادمي ثم تحقق مجدد عند الطلب.
- رفع ملف استيراد خاص، فحص ومعاينة واعتماد واستئناف ونشر؛ cursor/progress/idempotency واضحة، لا نشر جزئي.

لا نبدل API القديمة قبل وجود طبقة توافق واختبارات الفرع والمراجعة والحذف. عدم وجود مستند تسجيل لا يمنع إنشاء/تقديم النشاط؛ الموافقة لا تأتي من جسم الطلب.

## ما بُني الآن

backend/merchant-platform/domain.js: تطبيع هاتف العراق، عقد ملف الشخص ومسودة الأنشطة الثلاثة، إزالة حقول الشهادة الصحية/الملكية/الاعتماد الواردة من النموذج، شهادة تسجيل اختيارية، أهلية الفرع، قوالب صلاحيات، تحقق إصدار العضوية والجهاز والجلسة والنطاق، منع تصعيد التفويض، وتسعير الخيارات بالدينار من المصدر مع snapshot. اختبارات محلية للحالات الأمنية والخيارات والأسعار والأدوار؛ الوحدة غير مربوطة بالخدمات المنشورة بعد.

## العمل التالي الملزم

حصر حي كامل دون بيانات شخصية مكشوفة للملكيات والعضويات والمحافظ والملفات والطلبات، ومصفوفة صلاحيات لكل مسار، وحسم جدول هوية الشخص الفعلي. بعدها storage/fences/فهارس وترحيل dry-run قابل للتكرار، ثم التسجيل ومساحة الأعمال. إنشاء جداول أو نشر guards لا يتم قبل تثبيت عقد التوافق مع التطبيقات الثلاثة. حسابات الاختبار الحالية محفوظة، ولا OTP أو تحويل مالي ضمن الجرد.


## عقد إعدادات الإنشاء المركزي

BusinessTypePolicy وOnboardingSchema بإصدار ومعرفات حقول ثابتة ومراجعة/اعتماد في Settings. GET إعدادات منشورة فقط حسب النوع/المنطقة/قدرات إصدار التطبيق؛ API الموظفين لمسودة/معاينة/طلب اعتماد/نشر/رجوع. POST المسودة والتقديم يحمل configVersion، والخادم يحمّل السياسة المرجعية ويعيد فحص فتح التسجيل حيًا. لا يقبل قواعد أو حالة اعتماد أو هوية مالك يرسلها العميل.

domain.js الحالي يثبت الأنواع الثلاثة كبداية فقط؛ قبل ربطه بالإنتاج التشغيلي يُستبدل التحقق الثابت بسجل الأنواع والسياسة المنشورة ذات القدرات المدعومة. الحقول والشهادة الاختيارية تُقرأ من الإصدار المعتمد؛ ضوابط الهوية والتفويض تبقى ثابتة غير قابلة للتعطيل. تفاصيل القرار ومعايير القبول في القسم 18 من خطة الانتقال.


## تحديث التنفيذ
