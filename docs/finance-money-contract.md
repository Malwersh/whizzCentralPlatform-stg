# عقد المبالغ المالية — الجزء الأول من الخطة الموحدة

التاريخ: 2026-10-15. النطاق: Staging. الحالة: **وحدة حساب وتحويل محلية مكتملة باختباراتها؛ غير مربوطة بالمسارات التشغيلية وغير منشورة**. المرجع: [الخطة الموحدة](finance-pricing-settlements-returns-unified-plan.md).

## 1. نتيجة فحص الوحدات الموجودة

| المسار | العقد الموجود المثبت في المصدر | أثره على الربط القادم |

هذا جرد موجه لعقد الوحدة، وليس إعلان اكتمال جرد كل كتّاب الأموال والمستهلكين في المرحلة 0. لم تفحص بهذه الخطوة سجلات أشخاص أو أرصدة تاريخية ولم يعاد استدعاء AWS؛ تستند حالة المنشور إلى بيان الفحص المؤرخ أعلاه.

## 2. شكل المبلغ الجديد

تنفذ [money.ts](../backend/wallet-service/src/money.ts) العقد التالي داخل خدمة المحفظة المالية القائمة؛ لا خدمة أو جدول أو محرك دفع جديد:

```json
{"currency":"IQD","scale":1000,"moneySchemaVersion":1,"minorAmount":3500125}
```

المثال يساوي 3500.125 دينار. يقبل العقد أعدادًا صحيحة آمنة فقط من سالب إلى موجب Number.MAX_SAFE_INTEGER بالأجزاء؛ الأعداد السالبة مسموحة حسابيًا للتعديلات والعكس. يحتاج كل مسار أعمال تحققًا مستقلًا من الإشارة والحد التجاري والأهلية، فصحة Money لا تمنح إذن دفع أو تسمح بسعر منتج سالب.

عملة أو وحدة أو إصدار مفقود/مختلف يرفض دون افتراض. readMoney يفك كائن المبلغ وحده ويرفض حقوله الأجنبية، وليس سجل الطلب كله. البيانات الواردة unknown تخضع لهذا القارئ قبل الحساب. يعيد العقد كائنًا مجمدًا قابلًا لتسلسل JSON؛ لا يخرج BigInt إلى API أو DynamoDB.

## 3. العمليات المنفذة

| الدالة | السلوك |
|---|---|
| moneyFromMinor / readMoney | إنشاء قيمة صحيحة أو التحقق من كامل علاماتها دون تخمين |
| parseIqd / formatIqd | إدخال عشري نصي دقيق حتى ثلاثة منازل وإخراج نص قياسي؛ يمنع الترميز الأسي والفواصل والكسور الأطول، ولا يقبل number عشريًا بديلًا عن النص |
| fromWholeIqd | تحويل صريح من دينار صحيح مثبت الوحدة إلى أجزاء؛ يرفض تجاوز الحد |
| toWholeIqdExact | جسر إلى المحفظة القديمة فقط إذا كان المبلغ يقبل القسمة على 1000 دون باقٍ؛ لا يقرب ضمنيًا |
| addMoney / subtractMoney | جمع وطرح بأعداد صحيحة عبر BigInt داخليًا؛ فحص الحد في الناتج النهائي |
| multiplyMoney | تطبيق معدل بسط/مقام صحيحين دون ضرب عشري تقريبي، مع تقريب مختار صراحة |

parseIqd يستقبل أرقام ASCII بعد تهيئة الإدخال في الواجهة؛ لا يفسر الأرقام العربية أو فواصل الآلاف من نفسه. formatIqd نص مالي قياسي؛ تنسيق العرض العربي وفواصل الآلاف وظيفة واجهة مستقلة ولا يعاد إرسال النص المحلي بوصفه قيمة خام.

التقريب المدعوم: EXACT يرفض فقد الأجزاء؛ TOWARD_ZERO يحذف الباقي باتجاه الصفر؛ HALF_AWAY_FROM_ZERO يقرب النصف بعيدًا عن الصفر بصورة متناظرة للعكس. لا توجد سياسة تقريب افتراضية؛ تبقى قاعدة كل رسوم/اتفاقية وترتيب تطبيقها جزءًا من نسختها التجارية قبل التفعيل. لا تحسب هذه الوحدة عمولة أو أجرة أو حجزًا ولا تختار سعرًا.

أخطاء MoneyError ذات رموز ثابتة: INVALID_MONEY وUNSUPPORTED_MONEY_SCHEMA وMONEY_OVERFLOW وPRECISION_LOSS وINVALID_ROUNDING. تحول API هذه الرموز لاحقًا إلى رسائل مستخدم مناسبة دون تسريب قيم حساسة.

## 4. ضوابط الربط والهجرة

1. السجل الجديد يعلن العملة والوحدة والإصدار، ويرتبط بمرجع الكاتب/Quote والقاعدة في غلاف العملية. هذه العلامات تصف الصيغة ولا تثبت صحة مبلغ العميل؛ الخادم يعيد التسعير والتحقق من المصدر.
2. السجل القديم بلا علامات يحتاج محولًا محددًا لعقد كاتبه بدليل مستقل. اسم الحقل أو كبر العدد أو عملة IQD وحدها لا تكفي لتحديد scale. الغامض يبقى غير مصنف ولا يحصل على مبلغ مفترض.
3. fromWholeIqd دالة تحويل صريحة وليست قارئًا تلقائيًا للسجلات؛ تقع مسؤولية إثبات عقد المصدر على محوله. لا يستخدمها المسار العام لاختيار وحدة بالحدس.
4. لا يكتب ناتج Money إلى availableBalance/lockedBalance/amount القديمة بالأجزاء. يستخدم جسر الدينار الدقيق بعد إثبات عقد الهدف، أو يمنع العملية التي تتطلب أجزاء حتى ترقية مخطط الرصيد وجميع كتّابه بإصدار ومطابقة.
5. لا تضرب الأرصدة أو ledger التاريخي في 1000 بالجملة، ولا يعاد حساب مبالغ طلبات سابقة أو إصلاح فروق غير مفسرة. تبقى الحراس المركزية والحذف والتدقيق ومنع التكرار مطلوبة في الربط القادم.
6. عند ربط خدمة أخرى، تستخدم العقد المرجعي نفسه مع فحص تطابق التغليف؛ لا تنسخ الحساب يدويًا إلى واجهة Flutter. لا يغير نشر الوحدة وحدها مسارًا لا يستوردها.

## 5. التحقق والحدود والخطوة التالية

نجح npm run build في backend/wallet-service، بما فيه فحص تطابق محرك الموظف المرجعي. نجح node --test test/*.test.cjs: **153 اختبارًا، صفر فشل أو تخطٍّ**، منها **12 اختبارًا جديدًا** في [money.test.cjs](../backend/wallet-service/test/money.test.cjs). تغطي شكل JSON، غياب العلامات واختلافها، رفض القيم غير الآمنة، دقة التحويل النصي، أقصى المبالغ الموجبة والسالبة، رفض الكسر عند جسر المحفظة، ودقة معدلات ذات ضرب وسيط كبير والتقريب وعكس الإشارة ومئات حالات الذهاب والإياب.

لا تحتاج هذه الدوال الخالصة اختبار بيانات فعليًا أو IAM؛ لم تكتب بيانات ولم تضف مسارًا أو إذنًا أو اعتمادًا، ولم تبن أو تثبت تطبيق هاتف. لا تعد نهاية المرحلة 0 أو أساس Journal المكتمل أو تفعيل المال الجديد. الجزء التالي يبدأ بإعلان نطاقه للمستخدم، ويكمل عقود توزيع مبالغ COD/Prepaid واستحقاق الأطراف واختبار الأمثلة قبل ربط كتّاب الأموال.
