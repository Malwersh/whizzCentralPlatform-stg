# تشغيل حذف الحسابات والاحتفاظ والاستعادة — Staging

تحديث 2026-10-14. لا تتضمن هذه الوثيقة تصريحًا بنشر Production.

## سياسة التشغيل

- البيانات الشخصية التشغيلية: تُنظف عند استيفاء التحقق والتسويات وفق السياسة الحالية، مع الموانع الموثقة.
- السجلات المالية اللازمة: 7 سنوات وفق النسخة المعتمدة لكل طلب؛ عامل الانتهاء يفحص المصدر وجميع نسخ أرشيفه، ويمنع الحذف عند مانع أو مدة أطول.
- أُوقف TTL المالي؛ TTL لا يراجع موانع الاحتفاظ. انتهاء الأرشيف والمصدر ينفذ بمعاملة مشروطة، وليس بتنظيف غير منسق.
- اعتمد المستخدم 35 يومًا لنسخ التشغيل في 2026-10-14. نسخ DynamoDB اليدوية الـ23 الحالية دخلت سجل السياسة دون حذف، مع 35 يومًا من التسجيل للانتقال. النسخ الجديدة في النطاق المسجل تتبنى 35 يومًا عند اكتشافها؛ هذا يعني أن الكشف اليومي قد يضيف أقل من يوم إلى المدة الفعلية.
- الاستعادة الزمنية الحالية لسجل الحذف 35 يومًا؛ لم توجد خطة AWS Backup في الحصر الحالي. النسخ غير المسجلة أو خارج قائمة الجداول المعتمدة لا تُحذف تخمينيًا. لا يشمل العامل حساب AWS القديم.
- الأرشيف المالي منفصل عن نسخ التشغيل. لا يُستخدم حذف نسخة تشغيلية لاختصار مدة الاحتفاظ بالسجل المالي الأصلي.
- الموانع `legalHold` و`retentionHold` تطبق على المصدر وأرشيفه وسجل النسخة. إضافة مانع إلى نسخة بعد بدء DELETING ليست عملية مسموحة؛ يجب وضعه قبل اعتماد الإزالة. التعديل المباشر عبر صلاحيات AWS الإدارية خارج مسار التشغيل يحتاج حوكمة مستقلة.

## فحص دوري

عامل الحذف الأساسي كل دقيقة، وعامل الموظفين كل دقيقة، وانتهاء السجلات المالية والنسخ يوميًا. تعرض النتائج عدد المنفذ والمحجوب والتقدم الناقص، دون طباعة هواتف أو JWT أو OTP أو PIN.

استخدم استدعاء Lambda مع `{ "dryRun": true }` للحصر. الاستدعاء الافتراضي للمالية والنسخ للقراءة فقط. التنفيذ يحتاج العلم المنشور و`dryRun:false`. لا تغيّر بيانات فعلية لتبدو قديمة لغرض التجربة؛ استخدم فقط fixtures معزولة كما في `scripts/verify-deletion-completion-staging.py`.

## حذف موظف المنصة

من صفحة الموظفين، يُوقف الموظف أولًا وفق مسار الصلاحيات، ثم يسجّل موظف مخول طلب حذف. الموظف المستقل المخول يعتمد الطلب بعد دخول حديث وMFA. لا يجوز طلب حذف الذات أو اعتماد الطلب من المنشئ أو الشخص المستهدف؛ حساب bootstrap محمي.

العامل يزيل الصلاحيات والهوية ويُنظف النسخ الشخصية داخل جدول الموظفين، ويحتفظ بمعرف داخلي وحالة DELETED لمراجع التدقيق ومنع إحياء الهوية. لا يغيّر المبالغ أو ledger. حذف موظف المنصة ليس مسار حذف العميل أو السائق أو موظف المطعم.

اختبار الاعتماد والصلاحيات شمل شروط الخادم والمعاملات محليًا. اختبار AWS استخدم موظفًا وهميًا بلا رسائل دعوة واختبر العامل الحقيقي؛ لم يعتمد موظفان حقيقيان طلبًا عبر واجهة المتصفح في هذا الاختبار.

## بروتوكول الاستعادة

1. أوقف الكتابة للجزء المتأثر وحدد الجداول والوقت المطلوب دون إعادة Cognito أو الرموز الملغاة.
2. استعد إلى جداول جديدة بأسماء `RESTORE_QUARANTINE_staging_...` دون ربطها بالتطبيق أو منحها أذونات الخوادم الحالية.
3. استخدم سجل الحذف **الحي الحالي** وجدول الموظفين الحالي؛ لا تستبدلهما بنسخة تاريخية.
4. نفذ `AWS_PROFILE=Wizz_stg_UserApp node scripts/verify-restored-data-staging.cjs RESTORE_QUARANTINE_staging_NAME`. فشل القراءة أو حصر غير كامل يمنع تمرير الاستعادة.
5. هوية أو فرع محذوف أو عضوية أقدم من المغادرة تمنع تمرير النسخة. المرجع المالي المحفوظ وحده لا يبرر تمرير نسخة قديمة ببيانات شخصية؛ يلزم استعمال السجل المنظف الحالي أو إعادة معالجة النسخة مع مراجعة.
6. طلبات ACCOUNT الجديدة تحفظ manifest غير شخصي بمعرفات الهوية والملفات والمحافظ. طلبات الحذف التاريخية التي فقدت aliases أثناء الإكمال تفشل بـLEGACY_RESTORE_MANIFEST_REQUIRED؛ يُمنع تخمينها أو اعتماد الاستعادة قبل حصرها المستقل. قد تبقى النسخة بالحجر حتى انتهاء مددها إذا تعذر الحصر.
7. راجع السجلات المرفوضة ونظف نسخة الحجر فقط، مع احترام الموانع والاحتفاظ المالي. أعد الفحص واختبارات الدخول والمحفظة ونطاق الفرع قبل تحويل المرور.
8. مراجعة بشرية مستقلة لنتيجة الفحص ومطابقة العدادات، ثم التحويل التدريجي ومراقبة الأخطاء. هذا بروتوكول استعادة بأداة تحقق؛ ليس حاجز IAM يمنع مسؤول AWS من إجراء استعادة يدوية مباشرة.

أُجريت تجربة AWS فعلية على نسخة اختبار معزولة: إنشاء Backup، ثم RestoreTableFromBackup إلى الحجر، رفض سجل الهوية المحذوفة، تنظيف النسخة المعزولة واجتياز الفحص للسجل الجديد. نجح اختبار انتهاء نسخة الاختبار مع احترام مانع الاحتفاظ ثم إزالة النسخة بعد رفعه. حُذفت جداول الاختبار وتأكد غيابها، وبقيت النسخ الأصلية الـ23 دون حذف. هذه تجربة استعادة فعلية لبيانات اختبار، وليست استعادة لكل جدول أو لكل نسخة تاريخية؛ مراجعة aliases القديمة تبقى شرطًا عند استعادة تلك النسخ.


## السجلات التقنية

اعتمدت الإدارة حد 35 يومًا؛ CloudWatch لا يدعم 35، لذلك نُفذت مدة 30 يومًا الأقرب دون تجاوز الحد، مع توثيق الفرق. طبق العامل السياسة على 108 مجموعات تقنية ضمن حساب Staging، ويعيد المراجعة يوميًا للمجموعات الجديدة. أزيل التسجيل الصريح لرقم الهاتف من مصادقة المطعم ونُشر الإصلاح. المالية وسجل التدقيق في DynamoDB منفصلان.

[وثائق CloudWatch](https://docs.aws.amazon.com/AmazonCloudWatchLogs/latest/APIReference/API_PutRetentionPolicy.html) توضح أن إزالة الأحداث المنتهية ماديًا قد تتأخر عادة حتى 72 ساعة، ونادرًا أكثر؛ إعداد retention ليس وعد حذف مادي لحظي.

## طلب الحذف من الويب والمتابعة

- [بوابة طلب الحذف — Staging](https://staging.d2vmebm1e1n95m.amplifyapp.com/pages/account-deletion.html): الحسابات الثلاثة مستقلة، دخول هاتف ثم موافقة ورمز حذف مستقل، وإيصال متابعة بعد انتهاء الهوية. لا يُحفظ access token في المتصفح.
- [متابعة طلبات التطبيقات](https://staging.d2vmebm1e1n95m.amplifyapp.com/pages/account-deletion-requests.html): قراءة فقط بصلاحية audit.read أو finance.read وبنطاق جميع المناطق؛ صفحات كاملة متتابعة، دون OTP أو manifests أو بيانات اتصال. ترتبط من Settings.
- نُشرت الصفحات في Amplify job 48 مع الحفاظ على بقية الموقع، ونُشر CORS والخادم. فحص preflight الفعلي أعاد 204 والأصل الصحيح وCache-Control:no-store.
- اختبارات Node: 171 للحذف و74 لخدمة الموظفين؛ Python: 3 لسياسة السجلات. اختبار Chrome ببيانات محاكاة اجتاز ثمانية مسارات منها الانقطاع والتسوية واكتمال الحذف وإعادة تحميل الإيصال وفصل التطبيقات، دون رسائل أو حذف حسابات فعلية. اجتازت شاشة المشرف Chrome أيضًا عرض نطاق العضوية، تحميل الصفحات، ورفض الصلاحيات. تحقق DescribeUserPool الفعلي أثبت دعم phone_number لتسجيل الدخول في المجمعات الثلاثة؛ لم تُرسل رسالة تحقق حقيقية من صفحة الويب في هذا الفحص.
- إعادة اختبار المتصفح: أداة Playwright مطلوبة، ثم NODE_PATH لمسار تثبيتها عند الحاجة، وتشغيل node scripts/test-public-deletion-browser.cjs. يستخدم Chrome المحلي واتصالات محاكاة فقط.

## حدود الإغلاق التشغيلي

اكتمال حذف بياناتنا لا يثبت إزالة سجلات مزود الرسائل OTPIQ. [سياسة OTPIQ](https://otpiq.com/privacy-policy) تعرض حق طلب الحذف لكنها لا تحدد مدة الاحتفاظ بسجلات الرسائل أو API لحذف بيانات مستلم بعينه. لا يعرف المستخدم سياستهم حاليًا. أُعدت أسئلة في docs/otpiq-retention-review-request.md ولم تُرسل. يلزم جواب موثق واعتماد مسار المزود قبل إعلان اكتمال دورة الحذف عبر جميع الأطراف.

لم يُنشر Production. رابط الإنتاج وسياسة الخصوصية وإقرارات المتاجر تحتاج مواءمة قبل الإطلاق. لم يُختبر اعتماد موظفين حقيقيين مستقلين للحذف عبر المتصفح؛ شروط التفويض اختُبرت محليًا والعامل على AWS بموظف وهمي. أداة الحجر شرط تشغيل موثق، وليست منع IAM مطلقًا لمسؤول AWS. لا تُغيّر هذه الحدود نتائج نجاح حذف المستخدم والسائق والمطعم والمالك وإزالة عضوية الموظف المختبرة.
